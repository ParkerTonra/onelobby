# OneLobby: make this game multiplayer

You turn a single-player game into one that players can host and join, and that keeps working after any server is gone
(a player hosts from their own machine and shares a join code). The user drives the choices; you propose them with
reasons. One file holds every choice: `onelobby.json` (at the game's root; Unity: `Assets/Resources/onelobby.json`; schema: `onelobby/blueprint.schema.json` in the
npm package; design: `docs/design/blueprint.md`). **In a clone of the OneLobby repo (an unreleased build), run
`node <clone>/clients/js/packages/create-onelobby/bin/create-onelobby.js ...` for every command below, and never `npx create-onelobby`:
`npx` fetches the published, older scaffolder (it answers `unknown option: --recommend`).** Build it first: `npm ci && npm run build` in
`clients/js`, then `node scripts/build.mjs` in `clients/js/packages/create-onelobby` (that exact folder, not `packages/client`; it prints nothing when it works); `--help` prints on its first line which build it is (a clone's or the
published package). Everywhere else the commands below are `npx create-onelobby ...`. The scaffolder's own rules are not repeated here: it answers,
you explain its answer. Run the phases in order. Never skip Verify. Never write "works": name the checks that ran.

## 1. Survey (read only, change nothing)

Note each finding with the file and line that told you:

- **Engine**: `project.godot` alone = Godot GDScript (`godot-gdscript`); `project.godot` with a `.csproj` = Godot C#
  (`godot-csharp`); an HTML page and JS = browser (`web`); a Node server that serves the page = `node-browser`; `ProjectSettings/`
  = Unity (`unity`); other .NET = `dotnet`. Anything else (Unreal, ...): stop, tell the user OneLobby has no client for it yet. Godot: read `config/features` in `project.godot`: the add-on and `verify` need **4.4 or newer**
  (`--into` refuses a project whose `config/features` names an older version, `godot_too_old`, and writes nothing), so with 4.3 or older stop and tell the user.
- **Loop**: fixed tick (`setInterval`, accumulator, `_physics_process`, `_PhysicsProcess`, `FixedUpdate`) or frame-driven.
- **Determinism**: RNG seeded and kept in game state vs `Math.random` / `randf()` / `UnityEngine.Random`; wall clock in the
  sim (`Date.now`, `Time.get_ticks_msec`, `Time.time`); unordered iteration; physics engine; floats.
- **Genre and pace**; **players** the design implies (map slots, spawns, else 4); **menus** (where a "Play together" entry fits);
  **pause** (what the Escape menu calls); **settings storage**; **build and test commands**.
- **What multiplayer it already has** (skip for a new game): its own menu, join-code or relay (TURN) paste field, settings storage, a copy of the add-on
  in `addons/onelobby/` (older pin file `PIN`, a `PIN.json`, or no pin), its own snapshot or session code, its own two-process test. Note each file; the section
  "A game that already has multiplayer" below says what to do with them. A **web or Node game** (own HTTP server, own sync and rooms, own handshake and version constants, rate-limit or timeout
  constants, a `package.json` that already lists `onelobby`) has no menu to find: its section is "A web or Node game that already has multiplayer" below, and it also names the constants to collect now. **A game whose only multiplayer UI is a room-code box** (no name field, no settings, no relay field, no menu) has nothing to replace in its page: note that now and say it in the report; only the constants, the hand-built kit and the failure texts change.
- **The game's own tests run local-only.** Before the baseline run of the game's own test suite, read how it starts hosts: a suite that binds all interfaces or reaches public relays (Nostr, STUN, a
  TURN or lobby server) needs the game's own env flag or argument for "this PC only" (grep the test files and the server file for `process.env`). Set it for the baseline and for every later run. **A game with no such switch gets one first (before any baseline run):** one env var or flag in the game's own host start-up that makes it and its own HTTP listener
  listen on 127.0.0.1 only and keep off public relays (Node: `process.env.<GAME>_LOCAL` -> `hostDirect(kit, { local: true, port: 0 })`; Unity: `runner.BindAddress = "127.0.0.1"`; Godot: the menu's `--local`), and run the game's own tests with it
  set; list the switch under "Built" in the report. Only when the user forbids a change before the baseline, run just the tests that need no network and say which you skipped. Never run an unknown suite first and read its log after. **A Node game on an older `onelobby` pin: install this build BEFORE adding the switch and running the baseline** (`npm install <clone>/clients/js/packages/client --install-links --no-save` in a clone, `npm install onelobby@^<version> --no-save` once released, plus `npm install --no-save node-datachannel@^0.33.4` if the folder has none): an old pin ignores `local`, and `bindHost` alone makes the join-by-code tests fail `direct_unreachable` (the code names the LAN address, the host listens on loopback). **Unity: the game's own PlayMode assembly may need a GPU: run it in batchmode WITHOUT `-nographics` (no window opens in batchmode); with `-nographics` its baseline fails wholesale (`RenderTexture.Create failed`) and is no baseline.** The scaffolder's own test and `verify` keep `-nographics`.
- **Game id and net version** of a game that already has them: grep its data and settings files for `game_id`, `gameId`, `net_version`, `netVersion` and their neighbours (`NetVersion`, `PROTOCOL_VERSION`, `PROTO`, a `version` sent in the hello or handshake; a tunables or
  config file, the old client's constructor). When the game has no such value, pick `1` and say so in the report (the game id is part of the saved-settings key, so decide it before any settings import). Pass them as `--game-id` and `--net-version` (`--yes` would invent `com.example.<folder>` and the version `1`), and the game's own name as `--title '<its name>'` (Godot: `config/name` in
  `project.godot`; `--yes` would take the folder name, so a game in `mygame/` would be titled "mygame").
- **One plain sentence** for the recommender: genre, **the engine named in the sentence itself** ("in Godot", "in Unity", "in the browser", "a Node server"; also when you will pass `--template`:
  a sentence with no engine answers `runCommand: null` and "no engine is known"), player count, and the tick rate when the game has one (a new game:
  leave it out; every game type has a default `tickRate`, and `why` says how to change it). Write "deterministic" only for what the
  survey proved (fixed tick, state-held seed, no wall clock, no unordered iteration), never as a hope. **An existing game whose Node process hosts the pages and keeps its own sync and rooms**
  says so in the sentence: "browser RTS, a Node server runs the match with its own server loop and its own rooms, 15 ticks a second" (`node` names the engine `node-browser`; "own server loop", "own sync" or "own rooms" name the shape `own-server`).

## 2. Recommend

`npx create-onelobby --recommend "<the sentence>" --json` writes nothing and needs no network. Read the one object:

- `answers`: `[key, value, why]` rows, each a blueprint key; they become the proposal. `shape` names the game type
  (`lockstep`, `coop-snapshots`, `replication`, `turn-based`, `own-server`); keep it for the report.
- A **new game has no code to survey**: its sentence is the only input, so write what the players do ("run and jump around an arena
  together", "co-op", "side view platformer"). Words like run, jump, arena, platform, move around, co-op lead to a shape by themselves (a
  player world: `fallback: "world"` in the result, with a note saying so) unless the sentence says turn based, puzzle, deterministic or lockstep.
- `shape: null`: the sentence matched nothing clearly. `candidates` (present only then) lists every shape that scored, best first. Answer each
  of `questions` from the survey where a file and line settle it, ask the user the rest, add the `add` words to the sentence and run again.
  When nobody can answer (a new game, no user at hand), use the top `candidates` entry: add its words to the sentence, run again, and say in
  the report that the shape was the recommender's best candidate. With no candidates at all, ask; do not invent a shape.
- Players that move in a 2D world: the recommender reads "2D", "side view", "top-down", "side scroller" and "platformer" as
  `sync.player.space` = `2d` (an explicit "3D" keeps the default `3d`). Say "2D" or "3D" in the sentence of a game with players.
- `limits`: what this engine's client or template cannot do yet (it wanted X, wrote Y). Tell the user, do not hide it.
- `advice`: `built-in` is a client feature to use; `by-hand` is work the game must do; `depends` waits on the engine.
- `engine.template` `"planned"`: the scaffolder cannot write this engine yet; take the by-hand path (4.5). `runCommand: null` with a built engine means the sentence named no engine: add it to the sentence and run again.
- **A Node process that hosts** ("a Node server runs the match", "the host's node process serves the page") is engine `node-browser` with `hosting.direct` true (the recommender reads the words `node` and `nodejs`);
  without them a browser game is engine `web`, which cannot listen (`hosting.direct` false). For an **existing** Node game the answer is `shape: "own-server"` (`sync.mode raw`, `session.pause off`, `hosting.direct` true,
  `hosting.server` false) plus a `notes` line: treat `lobby.maxPlayers` (a placeholder 4) as the one row to replace, with the game's own seat or room constant (`--max-players`), and fill the rows the recommender cannot see
  from the game's constants (section "A web or Node game that already has multiplayer", step 1). With no shape words (`shape: null`) the recommender still prints that note: add "own server loop" and run again.
- **Co-op where the host runs the world** (the host sends snapshots, joiners predict their own actions, "not deterministic" next to "co-op") is `coop-snapshots`, not
  the competitive `replication`: write "co-op" or "cooperative" and "the host runs the world" or "the host sends snapshots". A competitive word (shooter, versus, pvp,
  racing, physics, battle royale) keeps `replication`. **A co-op shooter: leave the word "shooter" out** and write "cooperative ... game, the host runs the world" ("a cooperative zombie game with guns, up to 4 players, the host runs the world and sends snapshots (not deterministic)"): with the word the answer is `replication`. A game that keeps its own sync passes `--mode raw` and ends in the same file either way. Both shapes answer `sync.mode replication`: for a game that keeps its own sync see "A game that already has multiplayer".
- **The survey wins over the sentence.** The matcher reads words and ignores code facts ("deterministic ... calls `Math.random`"
  still gives `lockstep`). When they disagree, fix the sentence ("not deterministic", the real tick rate) and run again; if that is
  not enough, correct a value with a flag (`--mode raw`, `--max-players 2`) or `--set key=value`: a flag beats the recommendation
  and the run lists it under `overridden` / `dropped`. Say each override in the report.

## 3. Propose

Preview, writing and downloading nothing: `npx create-onelobby --into . --template <engine> --recommend "<sentence>" --yes
--dry-run --json` (a new game: `npx create-onelobby my-game --template <engine> ...`). `--recommend` fills in its `answers` by
itself; add a flag only to override one (section 2), not to repeat them. Pass `--template` when you know the engine; without it
`--into` reads the folder (Godot, Unity, .NET or web files) and stops with `engine_unknown` when the folder tells nothing. `--yes` invents the game id `com.example.<folder>`; give the real one with
`--game-id`, and a game's own net version with `--net-version` (survey). The result holds `blueprint` (the file to be written), `files` (added or updated), `recommendation`,
`collisions` (game files that differ from what the run would write), `removed` (old add-on files that go) and `addon.replaces` (old version -> new). In words, the dry run says
`Add-on: <old> -> <new>` and lists every game file that collides under `Collides with files already in your game`: read both before the go.

Show the user a table `key | value | why` (the `why` of `applied` rows, else the survey's reason with file and line), the plan
(the command, the files it adds or changes, where the menu goes and which scene or page opens it) and the `limits`. If every value
is a schema default, build without stopping; otherwise stop for the user's go or edits. With no user at hand (an unattended run),
the task that started you is the go: build, and list every value that is not a schema default in the report. After the build, put the reasons in the
file: one key named exactly `"$comment"` in each object (`hosting`, `lobby`, `sync`, ...), holding the reasons for that object's
keys in one string. The loaders ignore that name only; any other spelling (`"$comment tickRate"`) fails as `unknown_key`. A run with `--from <file>` keeps the `$comment` keys of that file, in the same objects, so a file that already holds its reasons keeps them. `--force` never replaces an existing `onelobby.json` (the dry run lists it as kept): delete the file to write a fresh one.

## 4. Build

1. Run the previewed command without `--dry-run`; its "Next:" lines are part of the job. Godot downloads the WebRTC natives once
   (pinned, SHA-256 checked, anonymous; offline: `--webrtc-zip <file>`). Godot C# needs the .NET build of Godot and the .NET 8 SDK,
   and until a release is on NuGet `--packages-from <folder of .nupkg>`. Then `godot --headless --audio-driver Dummy --import --path .`
   (C#: first `dotnet build <the .csproj>`). Natives already in `addons/godot_webrtc/` are kept; the run says when their version is not the pinned one (a pin of ours records it, else it is "unknown") and `--force` replaces them with the pinned release, and `verify` warns on `natives` in the same case.
   A second Godot run changes nothing and keeps your `onelobby.json` (`--force` keeps it too); web stops with
   `exists`: edit by hand. **Unity needs the package tarball** at the path its manifest names (the "Next:" line says where; a manifest that already has a `com.onelobby.unity` line keeps it and never moves it (a game on an OLDER tarball: step 1 of "Unity, a game that already has multiplayer" below), and the line is only printed when the file it names is missing): a released game
   takes the release tarball (`com.onelobby.unity-<version>.tgz`, natives included); in a clone, or for an unreleased build, run
   `clients/unity/fetch-natives.sh` once (anonymous, SHA-256 checked download of the last released package for its WebRTC libraries; it
   writes them into the clone's `clients/dotnet/OneLobby.DataChannel/runtimes/`; both scripts need bash, Git Bash on Windows), then `clients/unity/build-unity-package.sh --pack`,
   and put the new `.tgz` there (a tarball that lives somewhere else is not copied: pass `--package-from <tgz>` and the manifest gets a `file:` line to it, relative to `Packages/`). `--pack` stops with `PACK_FAIL` when `Runtime/Plugins/x86_64/datachannel.dll` would be missing, and `verify`
   fails `package` for a tarball without it: on Windows two peers never link. Your own code that uses OneLobby from its own `.asmdef` lists
   `OneLobby.Unity` in `references` (and `OneLobby.Replication.dll` in `precompiledReferences` for the player layer).
2. **Wire the drop-in menu where the survey said** (a new project has it as the main scene; a new Unity project has nothing to wire:
   its `Boot.cs` adds the menu when the first scene loads, the game's `AGENTS.md` says where). Godot `--into` never edits your scenes:
   instance `addons/onelobby/menu/menu.tscn` (C#: `addons/onelobby_menu/OneLobbyMenu.tscn`) in the menu entry's scene (it is a
   Control; a Node2D scene can hold it as a child). GDScript: give it the client before the menu's own `_ready`, so from the
   parent's `_enter_tree` (`$Menu.client = Net.client`) when the menu sits in the scene file, or before `add_child` when you
   instance it in code (`Net` is the autoload the scaffolder registered). Connect `game_started(lobby)` (start the match),
   `returned_to_lobby` and `left` (end it), keep a way to play alone. Restyle and reword: `docs/recipes/menu.md`.
   **Inside your own panel or container** the menu (a full-rect Control with no minimum size of its own) needs a size: in a `Container` parent give it `menu.custom_minimum_size = Vector2(520, 460)` and
   `menu.size_flags_horizontal = Control.SIZE_EXPAND_FILL` (and `..._vertical`) before `add_child`; in a plain `Control` or `Panel` parent it fills the parent through its full-rect anchors, so size the parent (the same 520x460 minimum
   is a workable floor for the room page; tune it).
   **Order when you hand over to your own session: `game_started(lobby)` fires with the menu's screen already PLAYING, so set your own role and "line is live" state FIRST, then attach the lobby.** Code that refreshes on the
   lobby's roster signals while the menu says PLAYING reads your state at once; a panel that finds no live line then hangs up (`menu.leave()`) and both peers drop the moment the match starts. Wrong: `attach(lobby); role = ...`;
   right: `role = ...; attach(lobby)`. The host's `game_started` comes after the room's countdown (3 s by default, `room.countdown_seconds`), with `start_on_host` too: the world keeps ticking solo for that time, and your
   session attaches only when the signal arrives.
   **Handing over to a game's own session** (the add-on's `menu.gd` comment has the same list): `game_started(lobby)` fires on every copy when the match starts
   (the host after its Start and the room's countdown, a joiner when the host's phase turns `in_game`, also a late joiner) and hands over the `OneLobbyLobby`
   (`lobby.local_peer_id`, `lobby.host_peer_id`, `lobby.is_host`, `lobby.room.players()`; in raw mode `lobby.send`, `lobby.broadcast` and `lobby.message_received` carry
   the game's own bytes). The menu has a room step the old flow may not have had: after Host or Join the lobby page shows the roster, Ready and the host's Start;
   nothing starts until the host clicks Start. With `pump` on (the default) the menu turns the client's `auto_pump` off and pumps it from its own `_process`, so the pump stops when the menu is freed: set
   `menu.pump = false` on a menu inside a node the game frees or replaces when the match starts (the autoload's client then keeps pumping itself). The menu reads `--host`, `--join=<code>`, `--name=<name>`, `--local` and `--autostart` from the command line itself: a game that reads flags of
   those names too would act twice (both copies host), so set `menu.boot_flags = false` and open the host or join yourself (`menu.model.apply_local()` for the
   127.0.0.1-only setup). The process flags are read once per process: the first menu that builds takes `--host`, `--join`, `--name` and `--autostart` and every later menu
   (a game that builds one in each world) acts on none of them (`--local` stays on for all), so a game needs no flag of its own for that. A menu built in code (a runtime CanvasLayer, no scene file): `var menu: OneLobbyMenu = load("res://addons/onelobby/menu/menu.tscn").instantiate()`,
   `menu.client = Net.client`, then `layer.add_child(menu)`: the client and every export are set before `add_child`. The "Next:" lines name both ways (scene and code).
   **Unity (its own terms; the GDScript names above do not exist there).** The component has `Pump`, `AutoHideOnStart`, `BootFlags`, `StartOnHost`, `BeforeHost`, `Runner` and `Client`: no `--autostart`. `StartOnHost = true` (set before the first frame) makes the menu press Start itself once after Host, so a game that hosts from its running world, or has its own room screen after the menu, does not make the host press Start twice. To start both copies with no click (a headless two-copy test) set `room.autoStart` to `"players"` and `room.autoStartPlayers` to `2` in `onelobby.json`: the room's countdown then runs and `GameStarted` fires on both copies; without either the host clicks Start. A game that reads its own `--host` / `--join` sets `menu.BootFlags = false`, or both copies act on the flag. `GameStarted` runs with the menu's screen already PLAYING, as in GDScript: set your own role and "line is live" state first, then attach the lobby; `ReturnedToLobby` and `Left` end the match. A game with its own runner or client (any class name) adds `OneLobbyRunner` itself FIRST and sets `Blueprint` and `ConfigureConfig` before anything reads `runner.Client` (the client is built on first use), then adds the menu, which takes the runner it finds (or set `menu.Runner`); a menu added first adds a runner of its own and builds the client at once. **A game that already has its own runner, Setup page and Room screen: the ordered recipe is "Unity, a game that already has multiplayer" below (steps 1 to 10), and the member signatures are in `docs/recipes/unity.md`.**
   **Test on this PC only.** The menu acts on `-- --host` and `-- --join=<code>` by itself, and a plain `--host` opens a port and
   reaches public relays. `--local` (127.0.0.1 only, no Nostr) is read by the GDScript menu itself, with no game code, as long as `boot_flags`
   is on; the C# menu reads it too (no lobby server, no check on open), and the "Next:" line's `OneLobbyNet.Wire(menu, args)` in the
   scene script's `_Ready` gives it the 127.0.0.1 host (`BootFlags` stays on). Never run `-- --host` without `--local`. `--local` also hands out and uses no ICE servers at all (no STUN lookup, so no server-reflexive candidate): a local run gathers host candidates only.
   **JS Node host, same thing:** a Node host has no flag, so `hostDirect(kit, { local: true })` is the JS `--local` (it sets `bindHost: "127.0.0.1"`, `openPort: false`, `nostr: false`; passing `bindHost` alone still asks the
   router and reaches public relays, so spell out those two too).
3. **Web** `--into` writes `onelobby.json`, `multiplayer/session.js` and `test/multiplayer.mjs` only: no menu (`ui.kind` stays
   `generated`, you draw the buttons; `--ui drop-in` is refused) and no `AGENTS.md`, and a minimal `package.json` only when the folder has
   none (an existing one is never edited: add `onelobby` as the "Next:" lines say, then `npm install`; a package.json with no `"type": "module"` (a CommonJS game) gets the glue as `multiplayer/session.mjs`, which Node reads as an ES module whatever the
   package says, so do not add `"type": "module"` to it). Put the game behind
   `step(tick, commands) -> hash`, `snapshot()`, `restore(tick, bytes)`, `hash()` and swap it into the test's stand-in `Game` (lockstep only: with `sync.mode` raw or replication the stand-in test proves OneLobby's lobby and messages, nothing of your game; keep your own sync and name your own two-player test as the proof).
   (A `node-browser` game does NOT use the glue in its page: see its paragraph below.) In the page go through `multiplayer/session.js`: `loadBlueprint()`, `makeKit(bp, { displayName })`, `kit.host()` or
   `kit.join(code)`, then `const s = bindSession(lobby, kit.blueprint, game)` before `lobby.start()`; call
   `s.pump(performance.now())` every frame and `s.send(bytes)` when the player acts; the match runs while `lobby.phase` is
   `"in_game"` (`lobby.on("phase", ...)`); keep the old loop for playing alone. A page with no bundler cannot resolve the glue's bare `onelobby` import: it needs the import map of
   `docs/recipes/js-web.md` section 1, and when your own server does not expose `node_modules/`, serve `onelobby/bundle` (`dist/onelobby.bundle.mjs`) at a URL and map `onelobby` to it (one line, in the "Next:" lines); the Host / Join / Start buttons and their errors are its sections 3 and 4. The `<one-lobby>`
   element (`menu.md`, "Web") fits only games that sync through its own `send` / `shared`, not through a Lobby.
   **`node-browser`** (a Node process hosts and serves the page): `--into <folder> --template node-browser` writes `onelobby.json` (`engine: "node-browser"`, `hosting.direct` true) and nothing else for `sync.mode` raw or replication: no glue, no menu, no stand-in test (`multiplayer/session.mjs` and `test/multiplayer.mjs` are written only for `sync.mode` lockstep; `verify` skips `project-test` for a raw or replication game). Without `--into` it stops (the game already has its server). **Everything else for this engine is in ONE place, the section "A web or Node game that already has multiplayer" at the end of this file** (the kit, `hostDirect`, CommonJS, seats, serving the page, the this-PC-only test, `describeError`, `verify`); other sections point there and repeat none of it.
4. Hand work the template does not cover, after 1 to 3: the game's sim as lockstep frames (`docs/recipes/godot-gdscript.md` section 4b,
   `js-web.md`), replication (`replication.md`), a pause-menu call when `session.pause` is not `off` (`pause.md`), the `by-hand`
   advice. Room (ready, countdown, kick, ban, rematch), saved settings, the connection check (it runs once when the menu opens, except with `--local` or in a headless run (no display), where it never runs by itself, so a game's own headless
   tests that build the menu reach no STUN server; `diagnostics.checkOnOpen: false` in `onelobby.json` switches it off everywhere, the button stays) and plain-language errors already live in the menu and the library.
   **Players in the world are not hand work on Godot or Unity any more:** when the recommendation has `sync.player.authority` (the `coop-snapshots` and `replication` shapes) or you
   pass `--mode replication --set sync.player.authority=owner|host` (add `--set sync.player.space=2d` for a side-on or top-down character: `sync.player.space` is `3d` or `2d`, default `3d`,
   so a 2D game without it gets a 3D player), the same one command writes the networked player: a new GDScript, C# or Unity project gets a character
   (`player.tscn`, `Player.tscn`, `Assets/Scripts/GamePlayer.cs`), a game with the spawner and a player check in its two-peer test (both ways: the joiner's player on the host and the host's player on the joiner, one `MULTIPLAYER_PLAYER` line each) (C# also vendors `addons/onelobby_net_player/` and references
   `OneLobby.Replication`; Unity needs neither, the package has the component); `--into` adds the vendored parts and prints the spawner lines to put where your game starts (it writes no scene into the game). The `--json` result
   has `netPlayer`. `verify` then has a `player` line. Web does not write it yet (`docs/recipes/net-player.md` sections 3 and 4).
5. **By hand** (`template_planned`, a planned engine): ask the tool, do not assume; its `template_planned` refusal
   names what it builds today. Follow the engine's recipe (`dotnet-generic.md`, `browser-game.md`; Unity is built now: `docs/recipes/unity.md` "One command"), write
   `onelobby.json` yourself against the schema, and say in the report that this path was by hand.
6. Rules that stay: read `onelobby.json` at run time, never copy its values into code (`OneLobby.fromConfig`,
   `OneLobbyClient.from_config`, `Blueprint.Load`); the game plays offline and every lobby call can fail (show `describeError`);
   the lobby server URL is a player setting; bump `game.netVersion` when command bytes change. **Relay list** (only when
   `hosting.nostr` is on; a web game on a lobby server skips this): the scaffolder writes the library's default list unprobed and
   some are dead. The check reaches public relays: run it only where that is allowed (a "nothing leaves the PC" test skips it and

## A web or Node game that already has multiplayer

Read at Survey when the game is `web` or `node-browser` and already has its own server loop, rooms, WebSocket or WebRTC code, version constants, an `onelobby` line in `package.json` or its own test. The Godot section below
is the Godot version of this one; nothing in it (menu, `user://`, `Net.client`, boot flags, olc) exists here. A Node host has **no menu to replace**: the pages only join, so skip the menu step entirely and leave the page's own
buttons and join link alone. **This is the one section for a Node host** (new game or existing); sections 4.3 and 5 (Verify) point here. Steps, in order:

0. **Install this build first** (and the game's own install, e.g. `npm ci`, when it has no `node_modules` yet) when the game's `onelobby` pin is older (no `OneLobby.fromConfig`, `hostDirect` ignoring `local`): step 4's command with `--no-save`, BEFORE the this-PC-only switch and the baseline run (Survey).

1. **Survey the constants** the game passes in code, and the key each one fills (the file is the one copy: delete the literal once it is read from the file). `--set key=value` sets any of them:
   - game id and its version or protocol constant: `game.id`, `game.netVersion` (`--game-id`, `--net-version`);
   - the seat cap of its own server or rooms, counted as the most browsers at once plus the host's own seat: `lobby.maxPlayers` (`--max-players`), never the match size;
   - its own pause: `session.pause` `off` (`--pause off`); its own seat-keeping token: `lobby.rejoin` false (`--no-rejoin`); late join: `lobby.lateJoin` (`--no-late-join`; a game with no late join of its own keeps the default `true`, as in the Unity section);
   - **rate limit** (messages per window it allows from one client): `session.rateLimit.messages` and `session.rateLimit.perMs` (`--set session.rateLimit.messages=60 --set session.rateLimit.perMs=2000`);
   - **peer timeout** (how long a silent client is kept): `session.peerTimeoutMs`, 0 or at least 6000 (`--set session.peerTimeoutMs=12000`); how long a joiner waits for the host: `session.readyTimeoutMs`;
   - its listen port: `hosting.directPort` (`--set hosting.directPort=<n>`; a busy port moves to the next of 9 ports and the join code carries it; `hostDirect` `fallbackPorts: 0` refuses that); page origins served elsewhere: `hosting.allowedOrigins`;
   - its name rules: `players.maxNameLength`, `players.identity`; the game's name: `game.title` (`--title`); no key feeds the lobby `name`: drop its literal and `hostDirect` names it `"<displayName>'s game"` (pass `name` only to keep the old text).
   Everything else is a schema default. A literal you leave in code next to the file is a bug (section 4, "Rules that stay").
2. **Recommend and propose** (sections 2 and 3) with the sentence of section 1; the answer is `own-server`. Pass what step 1 found as flags, so the dry run's table shows each non-default key with the file and line that told you.
3. **Build**: `npx create-onelobby --into . --template node-browser --recommend "<sentence>" --yes --game-id <id> --net-version <v> --title '<name>' --mode raw --max-players <n> --pause off --no-rejoin --set session.rateLimit.messages=<n> --set session.rateLimit.perMs=<ms> --set session.peerTimeoutMs=<ms>`
   (a clone's build runs as `node <clone>/clients/js/packages/create-onelobby/bin/create-onelobby.js ...`). It writes `onelobby.json` and nothing else (a lockstep game also gets `multiplayer/session.mjs` and `test/multiplayer.mjs`);
   there is no glue to delete and no menu. Add the `$comment` reasons (section 3).
4. **`package.json`** is never edited by the scaffolder. Move the pin and add the native module in one command, the exact line its "Next:" prints: `npm install onelobby@^<version in the Next line> && npm install --save-optional node-datachannel@^0.33.4`.
   An older `onelobby` pin (for example `^0.6.0`, which has no `OneLobby.fromConfig`) is replaced by that line, which also rewrites the lock file; right after a release add `--prefer-online` if npm answers `ETARGET`. When that version is not on npm yet (a clone, an unreleased build; npm answers `ETARGET` even with `--prefer-online`), install the clone's build instead: `npm install <clone>/clients/js/packages/client --install-links` (built first, see Install). Without `node-datachannel` `hostDirect` cannot link a browser. **Two side effects to say in the report and to undo before the game's PR:** the clone install writes a relative `file:../../.../clients/js/packages/client` path into the game's `package.json` and `package-lock.json` (it is only good on this PC); after the release run `npm install onelobby@^<released version>` to put the range back (or, for a test only, add `--no-save` and keep the range as it was); and `npm install --save-optional node-datachannel@^0.33.4` rewrites that range to the version it installed (`^0.33.4` becomes `^0.33.6`): restore the range the game pinned by hand if it pinned one.
5. **The Node process**: replace the hand-built kit and listen call. `OneLobby.fromConfig(json: unknown, overrides?: { displayName?: string; lobbyServer?: string; rememberSeat?: boolean; advanced?: { linkFactory, socketFactory, clock,
   wallClock, storage, playerIdStore, banStore, settingsStore, env, ... } })` reads everything else from the file; throws `bad_config` with the key's path. A test that needs another `netVersion` or `game.id` edits the parsed JSON before the call
   (`{ ...cfg, game: { ...cfg.game, netVersion: "99" } }`); it never needs the kit's source. `hostDirect(kit, options?: { http?, port?, bindHost?, local?, openPort?, nostr?, fallbackPorts?, maxPlayers?, rateLimit?, allowedOrigins?, password?, lateJoin?, name? })` from `onelobby/direct`
   takes each option from the file and an option you pass wins; per-run knobs (port, `openPort`, `nostr`, `local`) stay as the game's own flags or env. **A default in the game's own wrapper beats the file:** `startOneLobby({ port = 47810, openPort = true, nostr = true })` hands those literals to `hostDirect`, so `hosting.directPort`, `openPort` and `nostr` in `onelobby.json` are never read. Remove such defaults (default them to `undefined` and pass an option only when the caller or an env var set it, so `DIRECT_PORT=0` still works per run); the same for `maxPlayers`, `rateLimit` and `name` literals in the wrapper. CommonJS (`onelobby` is ES-module only; `require` fails before Node 22.12), inside an async function:
   `const { OneLobby, webRtcLinkFactoryFor } = await import("onelobby"); const { hostDirect } = await import("onelobby/direct"); const { RTCPeerConnection } = await import("node-datachannel/polyfill");`
   `const kit = OneLobby.fromConfig(JSON.parse(fs.readFileSync(path.join(__dirname, "onelobby.json"), "utf8")), { advanced: { linkFactory: webRtcLinkFactoryFor(RTCPeerConnection) } }); const lobby = await hostDirect(kit, { http: page });`
   `lobby.onConnection((conn) => { /* conn.peerId, conn.send(data), conn.onmessage = (e) => ..., conn.onclose = (e) => ... */ })` carries the game's own sessions unchanged (an ES-module game uses plain `import`).
   **`fromConfig` takes the PARSED object, never a path, a URL or a JSON string.** A game's own page helper or Node helper that used to take a hand-built option object (or the kit class, so a test can pass its own) takes the parsed file instead and calls `OneLobby.fromConfig(config, { displayName })` itself: the page passes `await (await fetch("/onelobby.json")).json()`; the Node host and every Node test pass `JSON.parse(readFileSync(path.join(__dirname, "onelobby.json"), "utf8"))` (ES module: `new URL("./onelobby.json", import.meta.url)`; a test that needs another value copies the object first, `{ ...cfg, game: { ...cfg.game, netVersion: "99" } }`). Pass it as one `config` option of the helper, so the file is read in exactly one place per side.
6. **The game's own HTTP server must serve what the page loads**: `hostDirect`'s `http` callback replaces the old listener (or the old server answers the same paths from the same function). It must return `/onelobby.json` and `/onelobby.bundle.js`
   (rules below); a page still served from the old port gets `403` on the WebSocket upgrade (Origin check): move it to `hostDirect`'s port, or list its origin in `hosting.allowedOrigins`. The one function serves every path: `/` (the page), `/onelobby.bundle.js` (`readFileSync(require.resolve("onelobby/bundle"))`; the page does `import { OneLobby } from "/onelobby.bundle.js"`, so no import map), `/onelobby.json` (`if (path === "/onelobby.json") return { type: "application/json", body: readFileSync(<absolute path of onelobby.json>) };`; the handler is `(path: string) => { status?, type, body: string | Uint8Array, headers? } | null`) and each script and asset of the game. A copy of the page deployed as static files needs `onelobby.json` beside it. The page must be plain `http`: an `https` page may not open `ws://` to an IP.
   **Facts of this engine:** `lobby.maxPlayers` is the whole lobby and counts the Node host's own seat (the host is a peer): size it like a server (64 in the recipe), the most browsers at once plus one, never the match size the sentence said. The page only joins (`kit.joinDirect(location.host)`, `await lobby.ready`, `lobby.asWebSocket()`; no `bindSession`, no `kit.host()`); the Node side takes each page with `lobby.onConnection(conn)`. No host migration: when the Node process stops every page gets `onclose` code `1001` (`host_left`); keep the game's own redial loop (`lobby.rejoin`, `resume_token` and `kit.rejoinDirect` are for `Lobby` pages, not `asWebSocket` ones). A CommonJS game (`onelobby` is ES-module only, `require()` fails with `ERR_REQUIRE_ESM` before Node 22.12) imports inside an async function (step 5).
7. **The page** (fetch relative to the page, so a static copy under a sub-path works): `import { OneLobby, describeError } from "/onelobby.bundle.js"; const kit = OneLobby.fromConfig(await (await fetch(new URL("onelobby.json", document.baseURI))).json(), { displayName }); const lobby = await kit.joinDirect(location.host); await lobby.ready; const ws = lobby.asWebSocket();`
   then the game's own message code on `ws`. Its own error code list (the one that decides "stop retrying") stays; its texts for join failures go: show `describeError(err)` (`{ code, message, hint? }`). **A helper that decides by code needs the error object:** change `joinStopNotice(code)` to `joinStopNotice(err)`, keep the code list (`STOP.has(err.code)`) and return `describeError(err).message`. **Where `describeError` comes from:** a page imports it from `/onelobby.bundle.js` (with `OneLobby`); Node code (the host, a test) from `onelobby` (CommonJS: `const { describeError } = await import("onelobby")`). A page module that Node tests also import cannot import a URL, so hand the function in (a parameter, or a `useDescribeError(fn)` setter the page's loader calls after it imports the bundle) instead of importing it at the top. **The wording differs from the game's own** (a version mismatch reads "You have version 1, the host has 2 ...", not the game's sentence): the game's tests that asserted the old texts change to the new message or to `describeError(err).code`, and a host-side notice for a joiner that failed (the `peerFailed` reason) gets the same swap (list those tests in the report). **A game that also hosts from a browser tab** (`hostNostr` in its page): the same `fromConfig` and constants apply (`hostNostr` takes seats, relays and the rate limit from `kit.blueprint` like `hostDirect`); `verify` never runs a browser, so name the tab host as not run in the report.
8. **What goes and what stays.** Goes: the game id, version, seat, rate-limit and timeout literals (read from the file), the hand-built kit and listen call, join-failure texts, a name or join-code field's storage and cleaning where the page has one
   (a page with no such field, only a room-code box, has nothing to replace: said at Survey, repeated in the report), and a test of lobby linking only. Stays: the game's sim, codec, rooms, handshake and redial or token rejoin (`--no-rejoin`), its pause, its in-world roster, and every test that
   drives its own sessions (rewrite the test's setup to `fromConfig` and `hostDirect(kit, { local: true, port: 0 })`, nothing else). Read `onelobby.json` at run time (section 4, "Rules that stay"): an edit of a value there must change the game.

With `port: 0` the host line reads `listening on TCP+UDP :<port>` and no longer prints a busy range (an older build printed `(0-<port> busy)`: harmless). Run the game's whole suite only

A test must import the game without starting its server: split the `listen` call out of a `server.js` that listens when loaded. `package.json` `scripts.test` is edited by hand.

Use `replication` only to replace that code on purpose (`docs/recipes/replication.md`). `--mode raw` leaves out `sync.tickRate` and `sync.player.authority` by itself (the run prints `left out sync.player.authority = owner`): do not pass them with it (`--set sync.player.authority=` with an empty value fails `bad_config`, and a value is dropped as `left out`).

Rewrite the script's flags to the menu's (`-- --host --local --autostart`, `-- --join=<the code the host printed> --local`; flags only after `--`) and say in the report which tests stayed. **A two-process script that lives outside the game folder** (a shell or CI script, not in the copy you were given): you cannot see or run it, so do not guess its contents; list it in the report under Next as "not seen, not rewritten" with the flags it must now use (`-- --host --local`, `-- --join=<code> --local`).
- **Environment variables** the client reads for one run: `ONELOBBY_NAME`, `ONELOBBY_RELAY` (a TURN line), `ONELOBBY_LOBBY_SERVER` and `ONELOBBY_LAST_CODE` (`spec/settings.md`; in JS, C# and GDScript alike). They replace a game's own
  name and TURN environment variables (for example a `GAME_TURN_LINE` in a test script: set `ONELOBBY_RELAY` instead); the library applies the relay to the host's and the joiner's ICE list, so the game's own relay wiring goes.
- **Rejoin**: a joiner's `rejoin_direct(code, token)` takes `lobby.code` of the lobby it was in (for an IP join the host's address code, for Nostr the grouped code) and `lobby.resume_token`; keep both before the line drops (the host's
  window is 60 s).
- **A game that builds its own `OneLobbyClient`** (in a service or autoload) switches to the autoload's: there is one client per process, `Net.client`. Delete the

  (the game's own line). Give the same client to the menu (`menu.client = Net.client`). The game's own service node may itself be named `Net` as a child of another node (`name = "Net"` under its main scene) beside the autoload: that is no clash, only a `/root/Net` node is.
- **A game that hosts from its running world** (no room, no Start button: the world is already up when the line opens) uses the menu for the part before the match and
  attaches its session in `game_started(lobby)`: the host builds its host session over the world that is already running, a joiner builds its join session and keeps its solo
  world until the host's first snapshot arrives. The menu's room step is not skipped by default; for a host that should not see it set `menu.start_on_host = true` (before `add_child`):
  after Host the menu presses Start itself, once, and `game_started` fires after the room's countdown. A joiner still sees the room and waits for the host.
- **A game whose multiplayer UI is an overlay in the world** (an F2 or Esc panel, a roster and Leave plate) keeps that plate for the match: the menu hides itself when the match
  starts (`auto_hide_on_start`) and shows again on `returned_to_lobby`, so the game's own in-match roster and Leave button (calling `lobby.leave()`) stay, and the menu is only the
  screen before the match.
- **A game that rebuilds its UI while a line is live** (a world swap, a scene change): a menu built then starts on its start page, because the menu does not adopt a client that is already in a lobby. Build the menu only while solo, free it when `game_started` has handed over, and build a new one when the line ends (`left`, `returned_to_lobby`). No call hands a live lobby to a menu (the menu has no adopt method in GDScript, C# or Unity), so the order is fixed: solo, menu, `game_started`, your own session, `left` / `returned_to_lobby`, a new menu. Not proven on a screen: what the start page does when built over a client that is in a lobby; do not rely on it.
- **Flags only after `--`**: the Godot menu reads `--host`, `--join=<code>`, `--name=`, `--local`, `--autostart` from the user args only. A game that took a plain `--host` now needs `-- --host`; remove the game's own handling of those flags (or set `menu.boot_flags = false`).
- **The game's now-unused net settings** (its own game id, lobby server URL, copy strings of removed fields in its data files): `grep` for each key; delete it when nothing reads it, else list it in the hand-off.
- **Settings**: the client's settings and the player id live in `user://onelobby.json` (the game's user-data folder, outside the game folder), not in the game folder. Two copies of one game on one PC share that file: the player id, name, relay, last code and the host's bans are the same for both, and each copy reads it once at start and rewrites the whole file on a change, so one copy's change can be lost by the other. That is fine for a two-copy test; for separate files give each copy its own store before first use (`client.store = OneLobbyStore.file("user://copy-b.json")`; JS `settingsFile`/`fileStore(path)`; C# and Unity an `IKeyValueStore`).
- **`sync.tickRate` in `--mode raw`**: unused (the game ticks itself); `--mode raw` leaves it and `sync.hashEveryTicks` out of `onelobby.json`, and the loaders' defaults apply when the keys are absent (a value you pass with `--tick-rate` or `--set` is kept).
- **Stays hand-built**: the game's session and snapshot code, its wire codec, its rejoin logic (`resume_token`; see "Host leaving and rejoin" below), its in-world roster, its
  solo start, and anything it adds to the net version at run time (`client.net_version = <its own value>` after `from_config` is the game's own line, not a copy of `onelobby.json`).
- **Old settings**: write the one-time import BEFORE deleting the old storage code, because it needs the old file path and keys (for example a `user://` settings file with its own section and keys for the name and the relay). Read the old name and relay line once and keep them: `client.settings.save({"name": old_name, "relay": old_line})` returns `{ok, rejected}` (a relay line that
  does not parse is rejected; list it under Next in the report). It runs once per player, not on every launch: import only when `client.settings.load_values()` holds no name yet, then erase the old keys from the old file (else every launch overwrites the name the player changed in the menu). Then delete the old storage code. If you do not carry them over, say why in the report (existing players start with an empty name and no relay).
- **Host leaving and rejoin**: a direct lobby (no `hosting.server`) has no host migration: when the host drops, the library ends the session for everyone (`hostLeaves: end`, the default and the only value a direct game can load; `--host-leaves migrate` refuses with `migrate_needs_server`) and no `host_changed` ever fires. A game that migrates its host by itself loses that on direct hosting: tell the user, or keep a lobby server (`hosting.server` true, `--host-leaves migrate` and not `--mode replication`) so the lobby does the migration. `--recommend` asks this itself (question `hostLeaves`) when the sentence mentions a host leaving or migrating and does not name a lobby server; answer it in the sentence and run again. A game with its own rejoin protocol (its own token over its own bytes) passes `--no-rejoin` (`lobby.rejoin: false`) so the library does not hold a seat that the game's rejoin also grants; one that uses the library's gives the joiner `rejoin_direct(code, token)` as above.
- **Its own pause**: `session.pause` comes out `host` for the co-op shapes, which is data for OneLobby's shared pause only. A game that already pauses itself passes `--pause off` (and keeps its own), or wires its Escape menu to `lobby.pause.request(...)` on purpose (`docs/recipes/pause.md`).
- **Constants that duplicate a blueprint key** (max players, a port, a tick or snapshot rate in the game's own code): replace them with a read of `onelobby.json` through the client when the game has a run-time client; do not keep both and make the file agree. The game's own wire constants (the net version) stay.
- **`advice` rows** that describe `ReplicationSession` (binary deltas, reliable keyframe, "built-in" prediction) do not apply once `--mode raw` is passed: leave them out of the report's Next.
- **The game's own error strings** for its own netcode stay: only join and host failures come from the menu (`describe_error`).
- **Autoload order and names**: the scaffolder puts OneLobby's `Net` first in `[autoload]` (Godot loads autoloads in file order and `Net._ready()` makes `Net.client`), so a game autoload that reads `Net.client` in its own `_ready` finds it; an older project that was edited by hand needs `Net` moved above them, or a lazy read. A game autoload that is also named `Net` stops the run with `autoload_taken` (a `class_name Net` or a node under `/root` is `name_clash`); no flag renames OneLobby's, so rename the game's: `grep` every `Net.` call, `"/root/Net"`, `get_node("Net")`, `has_node`, strings that build the path, scene and script paths in `.tscn` and `project.godot`.
- **A game that reads its own `--host` / `--join`** sets `menu.boot_flags = false` and then calls the menu's own functions from its own parse: `menu.model.apply_local()` (the `--local` setup), `menu.model.apply_autostart()` (a host that starts when the second player joins; without it the two-copy check waits for a Start click that nobody gives). Rewrite the `.olc` entry the scaffolder wrote to the game's real flags (it writes `-- --host --local --name=Host` and a second window with `-- --local --name=Joiner`). When the game's own netcode also opens a port, set that port from the `--local` run too: two copies on one PC otherwise collide on it.
- **The menu's pump**: with `pump` on (the default) a menu turns the client's `auto_pump` off and turns it back on when it leaves the tree, so a game that rebuilds its menu in every world builds each one with `pump = false` and leaves `auto_pump` on from the start.
- **The game's own `tests/multiplayer.gd`** is left as it is by `--into` (`kept`), and `verify`'s `direct` check then runs the game's file and passes on its `MULTIPLAYER_OK`. Move the game's lobby-linking test aside first (for example to `tests/own_multiplayer.gd`) so the add-on's takes its place, or say in the report that `direct` ran the game's own file.
- **Names**: `--into` refuses with `name_clash` when a script it adds would take a `class_name` or autoload name the game already has, or when a script puts a node named `Net` directly under `/root` (`name = "Net"` in a script that calls `root.add_child`) or looks up `/root/Net`, naming both files (a node named `Net` that is a child of another node is no clash and is let through); rename the one in the game
  and run again. It never writes a clash. The autoload is `Net` (script `net.gd`, no `class_name`): a game with its own node or autoload called `Net` renames that one (the check reads the scripts' text for `name = "Net"` next to `root.add_child` and for `/root/Net`, so a node put under the root another way still needs your own `grep`).
- **Unity, a game that already has multiplayer** (its own runner under any class name, its own Setup or menu page, its own Room screen, raw sync). `--into` an existing project writes no `.olc` entry (the new-project one builds `OneLobbyBuild.Windows` and runs `Builds/Windows/Game.exe`; point your own entry at the game's build, with `--host --local`; a second copy joins by the code the host's log prints, not a fixed port) and prints `game.title` came from the folder name: pass `--title '<name>'`. Do the steps in order; **every member, signature and a compiling code skeleton are in `docs/recipes/unity.md`, "`--into` a game that already has its own multiplayer": open it at step 4 and have it beside you for steps 5 to 8** (the names below are exact; the file has the full table, so you never read the package source or reflect over a DLL).
